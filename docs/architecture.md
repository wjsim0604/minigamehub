# 아키텍처 (architecture.md)

> 작성: planner 에이전트 / 검토: 사람
> 서비스 경계, 통신 방식, 데이터 소유권의 기준 문서입니다. CLAUDE.md의 서비스 표와 항상 일치해야 합니다.
> 최종 수정: 2026-10-14 (초안, 사람 검토 전)
>
> **주의:** 현재 CLAUDE.md 3장 서비스 표는 템플릿 예시(`user-service`, `order-service`, `example-py-service`)가 남아 있어 이 문서와 일치하지 않습니다. 이 문서 승인 후 사람이 CLAUDE.md 표를 갱신해야 합니다 (planner는 CLAUDE.md 수정 권한 없음). 아래 "CLAUDE.md 갱신안" 참고.

이 서비스는 단계적으로 구성합니다.

| 단계 | 범위 | 구성 | 관련 ADR |
|---|---|---|---|
| 1차 (MVP) | 게임 목록, 2048, 점프 게임, 로컬 최고 점수 | frontend 단독 (백엔드·DB 없음) | ADR-0003 (제안) |
| 2차 | 회원, 점수 제출, 게임별 리더보드 | frontend + gateway + user-service + score-service | ADR-0004 (제안) |

## 1. 전체 구성도

### 1차 (MVP)
```
[브라우저]
   └─ [Next.js frontend]
        ├─ 게임 레지스트리 (정적 데이터: 게임 목록)
        ├─ 게임 모듈: 2048, 점프 게임 (게임 로직 전부 클라이언트에서 실행)
        └─ localStorage (게임별 로컬 최고 점수)

백엔드 서비스, gateway, DB 없음. 외부 API 호출 없음.
```

### 2차 (랭킹) - 구성안
```
[브라우저] → [Next.js frontend] → [gateway] ─→ [user-service]  → user_db (MySQL)
                                           └─→ [score-service] → score_db (MySQL)

(선택) user-service ──이벤트──▶ [메시지 브로커] ──▶ score-service   ※ 필요 여부 미확정
```
- 게임 로직은 2차에도 클라이언트에서 실행합니다. 서버는 점수 저장·순위 계산만 담당합니다.

## 2. 서비스 목록과 책임

### 1차 (MVP)
| 서비스 | 책임(한 문장) | 소유 데이터 | DB | 스택 |
|---|---|---|---|---|
| frontend | 게임 목록 표시, 게임 실행, 로컬 최고 점수 관리 | 게임 레지스트리(정적), 로컬 최고 점수(브라우저 localStorage) | - | Next.js, React, TypeScript |

### 2차 (랭킹) - 구성안
| 서비스 | 책임(한 문장) | 소유 데이터 | DB | 스택 |
|---|---|---|---|---|
| frontend | 게임 실행 및 화면, 게이트웨이 API 연동 | 게임 레지스트리(정적), 로컬 최고 점수 | - | Next.js, React, TypeScript |
| gateway | 외부 요청 단일 진입점, 라우팅, 인증 토큰 검증, 속도 제한 | - | - | `<미정>` |
| user-service | 회원 가입·로그인, 인증 토큰 발급, 회원 프로필(닉네임) 관리 | 회원, 인증 정보, 프로필 | `user_db` | NestJS |
| score-service | 점수 제출 검증·저장, 게임별 리더보드 산출 | 점수 기록, 리더보드(집계) | `score_db` | NestJS |

- 서비스 경계 기준: 도메인(업무 영역) 단위로 나눈다. "누구인가(회원)"와 "얼마나 잘했나(점수)"를 분리한다.
- 게임 로직과 게임 목록은 서버 서비스로 분리하지 않는다 (게임 카탈로그 서비스는 관리자 기능 등 필요가 생길 때 재검토).
- Python 서비스는 현재 계획 없음.
- 새 서비스를 추가할 때는 책임과 소유 데이터를 먼저 이 표에 정의합니다.

### 게임 레지스트리 (1차부터 적용하는 원칙)
새 게임을 플러그인처럼 추가할 수 있도록, 게임 목록은 frontend 안의 **정적 레지스트리** 한 곳에서 관리합니다. 구체적인 파일 위치·인터페이스 코드는 frontend 에이전트가 정하되 아래 원칙을 지킵니다.

| 필드 | 설명 | 규칙 |
|---|---|---|
| `id` | 게임 고유 식별자 | 영문 소문자·숫자·하이픈(kebab-case). **한 번 정하면 변경 금지** (URL, localStorage 키, 2차 score-service의 `gameId`로 그대로 쓰임) |
| `name` | 표시 이름 | 예: "2048", "점프 게임" |
| `description` | 한 줄 설명 | 홈 카드에 표시 |
| `thumbnail` | 썸네일 이미지 경로 | 로드 실패 시 대체 표시 (FR-001) |
| `path` | 게임 화면 경로 | `/games/{id}` 규칙을 따름 |

- MVP 게임 id 제안: `2048`, `jump` `<사람 확인 필요>`
- 원칙
  1. **단일 등록 지점:** 게임 추가 = 게임 모듈 작성 + 레지스트리에 항목 1개 추가. 홈·라우팅 코드는 수정하지 않는다.
  2. **게임 간 독립:** 각 게임 모듈은 서로 import하지 않는다. 공통 기능(최고 점수 저장, 게임오버 오버레이, 입력 처리 유틸 등)은 공용 모듈로 두고 게임이 사용한다.
  3. **공통 생명주기:** 모든 게임은 동일한 진입/정리(마운트/언마운트) 방식과 점수·게임오버 알림 방식을 따른다. 화면 이탈 시 게임 루프·리스너를 반드시 정리한다. 2차 점수 제출은 이 "게임오버 알림" 지점에 연결한다.
  4. **지연 로딩:** 게임 코드는 해당 게임 화면 진입 시에만 로드한다.
  5. **로컬 저장 키 규칙:** `mgh:{gameId}:{항목}` (예: `mgh:2048:bestScore`). 게임별로 분리.
  6. 레지스트리 항목에 추가 필드(태그, 정렬 순서, 공개 여부 등)가 필요하면 하위 호환되게(선택 필드로) 추가한다.

## 3. 데이터 소유권
- 각 데이터는 **하나의 서비스만 소유**하고, 다른 서비스는 API 또는 이벤트로만 접근합니다.
- 다른 서비스 데이터가 필요하면 조회 API 호출 / 이벤트로 받아 로컬 복제 중 하나를 선택해 아래에 기록합니다.

### 1차 (MVP)
| 데이터 | 소유 서비스 | 참조하는 서비스 | 접근 방식 |
|---|---|---|---|
| 게임 레지스트리(목록) | frontend | - | 정적 데이터(빌드에 포함) |
| 로컬 최고 점수 | frontend (사용자 브라우저) | - | localStorage, 서버 전송 없음 |

### 2차 (랭킹) - 구성안
| 데이터 | 소유 서비스 | 참조하는 서비스 | 접근 방식 |
|---|---|---|---|
| 회원 정보, 인증 정보 | user-service | gateway(토큰 검증) | 토큰 서명 검증(공개키/공유 비밀 - 미정). gateway는 user_db에 접근하지 않음 |
| 회원 닉네임(표시 이름) | user-service | score-service(리더보드 표시) | **미확정 - 아래 후보 중 선택 필요** (A) 리더보드 조회 시 user-service 조회 API 호출 (B) `user.profile-updated` 등 이벤트로 score_db에 닉네임 복제 (C) 점수 제출 시점의 닉네임을 토큰 클레임에서 받아 함께 저장 |
| 점수 기록 | score-service | - | score-service API로만 조회 |
| 리더보드(집계) | score-service | - | score-service API로만 조회 |
| 게임 id 목록 | frontend(레지스트리) | score-service(제출 시 gameId 검증) | **미확정** - 후보: score-service 설정값으로 허용 gameId 목록 관리(레지스트리와 수동 동기화) |
| 로컬 최고 점수 | frontend (브라우저) | - | 서버로 이관하지 않음 (권장, 미결정) |

- score-service는 `userId`만 보관하고 회원 상세 정보(이메일 등)는 보관하지 않는다.
- user_db와 score_db 사이 JOIN·외래키 없음. `userId`는 값으로만 참조한다.

## 4. 서비스 간 통신

### 1차 (MVP)
- 서비스 간 통신 없음.

### 2차 - 구성안 (확정 전)
| 호출 | 방식 | 계약 위치 | 타임아웃 | 실패 시 처리 |
|---|---|---|---|---|
| frontend → gateway → user-service (가입·로그인) | REST | `docs/api.md` (2차 작성) | `<예: 3s>` | 오류 메시지 표시, 사용자 재시도 |
| frontend → gateway → score-service (점수 제출) | REST | `docs/api.md` (2차 작성) | `<예: 3s>` | 멱등 키로 재시도 1~2회, 실패 시 "점수 제출 실패, 다시 시도" 표시. 게임 자체는 영향 없음 |
| frontend → gateway → score-service (리더보드 조회) | REST | `docs/api.md` (2차 작성) | `<예: 3s>` | 리더보드 영역만 오류 표시, 게임 플레이에는 영향 없음 |
| score-service → user-service (닉네임 조회, 후보 A 선택 시) | REST | `contracts/<미작성>` | `<예: 1s>` | 재시도 1회 후 닉네임 대신 기본 표시(예: "플레이어")로 응답 |

- 원칙: 랭킹 관련 장애가 게임 플레이를 막아서는 안 된다 (모든 서버 호출 실패 시에도 플레이와 로컬 최고 점수는 정상 동작).
- 동기 통신 방식(REST/gRPC)과 메시지 브로커 도입 여부는 미확정.

## 5. 분산 처리 흐름 (Saga 등)
여러 서비스에 걸친 업무 흐름은 분산 트랜잭션 대신 이벤트로 처리하고, 실패 시 보상 동작을 정의합니다.

### 1차 (MVP)
- 해당 없음.

### 2차: 점수 제출 흐름 (구성안)
1. frontend: 게임오버 발생. 로그인 상태가 아니면 로컬 최고 점수만 갱신하고 종료 (로그인 유도 문구 표시는 선택).
2. frontend: 로그인 상태면 `gameId`, `score`, 멱등 키(클라이언트 생성 UUID), (부정 방지 수준에 따라) 플레이 세션 정보를 담아 gateway에 점수 제출 요청.
3. gateway: 인증 토큰 검증 → 사용자 식별자(`userId`)와 상관관계 ID를 붙여 score-service로 전달. 사용자별 제출 속도 제한 적용.
4. score-service:
   - 멱등 키 중복이면 이전 결과를 그대로 반환 (중복 저장 금지).
   - `gameId`가 허용 목록에 있는지, `score`가 게임별 허용 범위인지 검증. 실패 시 400.
   - 점수 기록 저장 후, 해당 게임 리더보드에서의 순위(또는 개인 최고 점수 갱신 여부)를 응답.
5. frontend: 응답의 순위/갱신 여부를 게임오버 화면에 표시.
6. 실패 시 보상: 단일 서비스(score-service) 내 처리이므로 보상 트랜잭션 불필요. 클라이언트는 같은 멱등 키로 재시도.

- 이 흐름은 score-service 단일 쓰기라 Saga가 필요 없습니다. 회원 탈퇴 시 점수 처리(삭제/익명화)처럼 여러 서비스에 걸친 흐름이 생기면 이벤트 기반으로 추가 설계합니다.

### 이벤트 후보 (미확정, 확정 시 `events.md`·`contracts/`에 정의)
| 후보 이벤트 | 발행 | 구독 | 용도 | 필요 조건 |
|---|---|---|---|---|
| `user.registered` | user-service | (없음) | 가입 통계 등 | 구독자 생기면 검토 |
| `user.profile-updated` | user-service | score-service | 리더보드 닉네임 로컬 복제 | 닉네임 접근 방식으로 후보 B 선택 시 |
| `user.deleted` | user-service | score-service | 탈퇴 회원 점수 삭제/익명화 | 회원 탈퇴 기능 정의 시 |
| `score.submitted` | score-service | (없음) | 업적·통계 등 향후 확장 | 구독자 생기면 검토 |

## 6. 인증·인가
- 1차(MVP): 인증 없음 (로그인 기능 없음).
- 2차 구성안
  - 외부 요청: 게이트웨이에서 토큰(JWT 등) 검증. 토큰 발급은 user-service. 로그인 방식은 미결정.
  - 인증 필요 범위: 점수 제출은 로그인 필요, 리더보드 조회는 비로그인 허용(제안).
  - 서비스 간 호출: `<서비스 토큰 / mTLS 미정>` - security-infra와 결정 필요.
  - 권한 모델: 일반 회원 단일 역할 (관리자 역할 없음).

## 7. 공통 사항
- 상관관계(trace) ID: `X-Request-Id` (제안, 2차부터 적용. gateway에서 없으면 생성)
- 로그 형식: JSON 구조화 로그 (2차 서비스)
- 헬스체크: `GET /health` (2차 서비스·gateway)
- 환경: `<local / dev / prod 구성 미정>`. MVP는 frontend 단독 배포.
