# 아키텍처 결정 기록 (decisions.md)

> 중요한 기술·구조 결정과 그 이유를 남기는 문서입니다 (ADR: Architecture Decision Record).
> 에이전트는 이미 결정된 사항을 임의로 뒤집지 않고, 바꾸고 싶으면 사람에게 제안합니다.
> 새 결정은 아래 양식을 복사해 맨 아래에 추가하고, 번호는 순서대로 올립니다.

## 양식
```
## ADR-000N: 제목
- 상태: 제안 / 승인 / 폐기 / 대체됨(ADR-000M)
- 날짜: YYYY-MM-DD
- 배경: 왜 이 결정이 필요한가
- 선택지: A, B, C (각각 장단점)
- 결정: 무엇을 선택했는가
- 이유: 왜 선택했는가
- 영향: 어떤 서비스·문서·코드가 영향받는가
```

## ADR-0003: MVP는 클라이언트 전용 게임으로, 백엔드 없이 시작
- 상태: 승인
- 날짜: 2026-10-14
- 배경: 1차(MVP) 범위는 게임 목록, 2048, 점프 게임, 로컬 최고 점수이며 로그인·랭킹은 2차로 확정되었다. 이 범위에는 서버에 저장하거나 서버가 판단해야 할 데이터가 없다. 또한 게임은 입력 반응성이 중요해 서버 왕복 없이 브라우저에서 실행되어야 한다.
- 선택지
  - A. 클라이언트 전용(frontend 단독, 게임 목록은 정적 레지스트리, 최고 점수는 localStorage)
    - 장점: 구현·운영 비용 최소, 장애 지점 적음, 빠른 출시, 오프라인에 가까운 동작
    - 단점: 기기·브라우저 간 기록 동기화 불가, 점수 위조 가능(MVP에서는 영향 없음)
  - B. MVP부터 gateway + game-catalog/score 서비스 구성
    - 장점: 2차 전환 작업 감소
    - 단점: MVP 요구사항에 없는 서버·DB·배포 파이프라인을 미리 운영해야 함, 출시 지연
  - C. 게임 로직을 서버에서 실행(서버 권위형)
    - 장점: 부정 점수 원천 차단
    - 단점: 지연에 민감한 1인 게임에 과도함, 서버 비용·복잡도 큼
- 결정: A. MVP는 frontend만으로 제공하고 게임 로직은 모두 클라이언트에서 실행한다. 게임 목록은 frontend 내 정적 게임 레지스트리로 관리한다.
- 이유: MVP 요구사항을 가장 적은 구성으로 충족하며, 게임 레지스트리 구조(고정 `gameId`, 게임오버 알림 지점)를 미리 갖춰 두면 2차에서 서버 연동을 추가하기 쉽다. ADR-0001(MSA)을 뒤집는 것이 아니라, 백엔드가 필요한 시점(2차)에 MSA 원칙대로 서비스를 추가하는 단계적 적용이다.
- 영향: frontend만 구현 대상. `docs/api.md`, `docs/events.md`, `contracts/`는 2차까지 비어 있음. CLAUDE.md 서비스 표 갱신 필요. 게임 `id`는 2차 `gameId`로 재사용되므로 변경 금지.

## ADR-0004: 랭킹 단계에서 user-service / score-service로 분리
- 상태: 승인
- 날짜: 2026-10-14
- 배경: 2차에서 회원, 점수 제출, 게임별 리더보드가 추가된다. ADR-0001(MSA)에 따라 서버 기능을 서비스로 나눠야 하며, 책임과 데이터 소유권을 정해야 한다.
- 선택지
  - A. 단일 서비스(예: ranking-service)가 회원과 점수를 모두 담당
    - 장점: 서비스 1개로 단순, 닉네임 조인 문제 없음
    - 단점: 회원/인증과 점수 책임이 섞임, 이후 회원 기능 확장 시 분리 비용 발생
  - B. user-service(회원·인증, `user_db`) + score-service(점수·리더보드, `score_db`) 분리, 앞단에 gateway
    - 장점: 책임 분리 명확, 점수 트래픽(제출·조회)과 회원 기능을 독립 확장·배포 가능
    - 단점: 리더보드 닉네임 표시에 서비스 간 조회 또는 이벤트 복제 필요, 운영 대상 증가
  - C. 회원은 외부 인증 서비스(IdP) 사용 + score-service만 직접 구현
    - 장점: 인증 구현 부담 감소
    - 단점: 외부 의존·비용, 로그인 방식 결정에 종속
- 결정: (제안) B. 2차 착수 시 gateway, user-service, score-service를 구성한다. 게임 로직은 계속 클라이언트에서 실행하고 서버는 점수 검증·저장·순위만 담당한다.
- 이유: 회원과 점수는 변경 이유와 부하 특성이 다르다. MSA 원칙(서비스별 독립 DB, API/이벤트 통신)에 맞고, 분리 비용이 가장 적은 시점은 처음 만들 때다. 단, 로그인 방식이 외부 IdP로 결정되면 C 또는 B의 user-service 축소를 재검토한다.
- 영향: gateway, user-service, score-service 신규. `docs/api.md`, `docs/events.md`, `contracts/` 2차 작성 필요. frontend는 게임오버 지점에 점수 제출·리더보드 화면 추가. infra에 MySQL(`user_db`, `score_db`)과 (필요 시) 메시지 브로커 추가. 미결정: 로그인 방식, 부정 점수 방지 수준, 닉네임 접근 방식(API 조회/이벤트 복제), 서비스 간 인증 방식.
